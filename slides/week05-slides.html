What is Prompt Engineering?

Prompt engineering is the practice of carefully designing, crafting, and refining the input text (prompts) given to generative AI models to elicit the most accurate, relevant, and desired output.

Prompt vs. Traditional Software Engineering

Prompt Engineering

  • Based on natural language
  • Behavioral steering
  • Probabilistic output
  • Iterative refinement

Software Engineering

  • Based on programming languages
  • Deterministic execution
  • Compilation / interpretation
  • Structured logic

An Iterative Process

Prompt engineering is fundamentally experimental.

  • A single prompt rarely yields optimal results
  • Refinement is required
  • Learning happens through iteration

Structure for AI Agent Prompts

  1. Role
  2. Task
  3. Requirements
  4. Instructions

Role

Defines the persona the model should adopt.
Influences tone, knowledge, and style.

“Act as a senior software architect.”

Task

The clear objective.

“Outline a project plan for a new microservices application.”

Requirements

Output constraints and formatting rules.

“The outline should be a numbered list with a maximum of five top-level items.”

Instructions

Execution guidance.

“For each microservice, provide a brief description and a list of its core dependencies.”

Prompt (User Message)

  • The prompt or the user message is the input to the AI agent
    • This is the request to the agent
  • It does not have to be a human
    • It can be other systems and even other agents

System message

  • System messages (also called System Prompts) define how the model should behave.
    • This is where you can get the agent to talk like a pirate – or something more useful

Three Layered System Message

  • Identity
    • “You are a helpful assistant.”
  • Developer Control
    • “Always respond in valid JSON.”
  • Guardrails
    • “If unsure, ask clarifying questions.”
  • Even if technically one message — conceptually, they are different layers.

Why Separate It Conceptually?

  • When prompts grow:
    • Harder to debug
    • Harder to version
    • Harder to evaluate
    • Harder to reuse across workflows
  • Think in software architecture terms:
    • Separation of concerns
    • Layered architecture
    • Maintainability
    • Modularity

Example – Poor Prompt Design

You are helpful.

Write clearly and professionally.

Well Structured Prompt Design - System Message - One message – Three Layers

You are an expert technical analyst writing for a professional audience.

You must always respond in valid JSON matching this schema:

{

“title”: string,

“summary”: string,

“risk_level”: “low” | “medium” | “high”

}

If required information is missing, ask a clarifying question instead of guessing. Never fabricate data.

Prompt Brittleness

  • Large Language Models can be surprisingly sensitive.
    • Small wording changes → large output differences
    • Hidden assumptions inside prompts
    • Sensitivity to tone, framing, and constraints
    • Implicit bias introduced by phrasing
  • This is called prompt brittleness (skrøbelighed).

Hallucinations & Grounding

  • LLMs do not “know” — they predict the most probable next token.
  • Hallucination Types
    • Fabricated facts
    • False citations
    • Invented statistics
    • Overconfident certainty
    • Even when the model sounds certain, it may be wrong.

Grounding the Model

  • To reduce hallucinations:
    • Retrieval-Augmented Generation (RAG)
    • External databases
    • Verified APIs
    • Tool-based answers
    • Clear uncertainty instructions
  • The more critical the task the more grounding is required.

Prompt Compression

  • As prompts grow, costs grow.
  • When Prompts Become Large
    • Token cost increases
    • Latency increases
    • Context window pressure increases
    • Noise increases
  • Long prompts are not always better prompts.

Prompt Optimization

  • Remove redundancy
  • Reduce verbose instructions
  • Externalize static rules
  • Move knowledge to RAG instead of inline context
  • Prompt engineering eventually becomes prompt optimization.

Types of Prompt Engineering

  • Zero-Shot
  • Few-Shot
  • Chain-of-Thought
  • Tree-of-Thought
  • RAG

Zero-Shot Prompting

  • A technique where an AI model is instructed to perform a task without being given any example inputs or outputs
  • Most basic prompt
  • Uses pre-trained knowledge only
  • Baseline approach
  • ⚠️ Limited by model knowledge

Few-Shot Prompting

  • an AI prompting technique where a model is provided with a few examples (typically 2-10) within the prompt to illustrate a desired task or format before asking it to generate a response for a new, unseen input
    • Add representative examples inside the prompt.
  • Demonstrates format
  • Demonstrates reasoning pattern
  • Improves reliability
  • ⚠️ Too many examples can reduce clarity

Chain-of-Thought (CoT)

  • a prompting technique for LLMs that improves reasoning accuracy by breaking complex problems into intermediate, logical, step-by-step steps before arriving at a final answe
    • “Let’s think this through step by step.”
  • Benefits:
    • Improved reasoning
    • Transparent logic
    • Easier debugging
    • More trustworthy output

Tree-of-Thought (ToT)

  • an advanced AI prompting framework that improves LLM reasoning by breaking problems into, exploring, and evaluating multiple, branching, and, and backtracking

  • Explores multiple reasoning paths in parallel.

    • Structured like a decision tree
    • Brainstorms alternatives
    • Can backtrack
    • Useful for complex planning

Retrieval-Augmented Generation (RAG)

  • an AI framework that improves LLM accuracy and relevance by fetching data from trusted, external knowledge bases before generating a response
  • Addresses static training data limitation.
    • Grounds output in external knowledge
    • Enables up-to-date responses
    • Supports domain-specific expertise

RAG introduction

Retrieval-Augmented Generation

LLM - challenges

  • LLMs generate answers using static training data, which can be outdated or incomplete
  • Training data is not up to date
  • No easy access to private or frequently changing data

Why RAGs?

  • Access to Up-to-Date Information: Unlike static models, RAG allows AI to provide recent, domain-specific, or company-private data without retraining.
  • Better Factual Accuracy: By grounding responses in retrieved documents, RAG reduces “hallucination” (fabrication of information) common in non-augmented LLMs.
  • Flexibility: RAG can be adapted to many domains (education, legal, medical, business) and is the foundation for applications like smart document assistants and chatbots.

Approaches to provide current data

  • Fine tuning
    • Retrain layers of the LLM with current data
    • Time consuming
    • Hard to keep LLMs up to date if data changes often
  • RAGs
    • Adds data to the LLM’s context window

RAG

The retriever

  • Locates and extracts pertinent data from external sources using keyword search or vector similarity search
  • Fetches relevant information to pass to the generator — e.g. search engine, vector database, …
  • The (user) query is used to retrieve the data

The augmentation

  • The retrieved data is added to the query/prompt

The generator

  • The LLM receives the original query plus the retrieved data, i.e. the augmented prompt

RAG Architecture and Process

  • Indexing/Preparation: External data is pre-processed and turned into numerical embeddings (vectors), often stored in a vector database for efficient retrieval.
  • Retrieval: On receiving a query, the system converts the query into an embedding and retrieves relevant documents or data chunks from the vector store.
  • Augmentation: The retrieved information is placed in the prompt using prompt engineering templates, making it available to the model during generation.
  • Generation: The LLM produces its output by combining its internal knowledge with the retrieved, up-to-date context, leading to more truthful and current responses.

Embeddings (Indexing/Preparation)

  • Embeddings are numerical representations of text, allowing models to compare meaning and context.
  • Example: “Coffee” and “Espresso” have similar embeddings; “Coffee” and “Cat” are far apart.
  • These representations are stored in a vector database.

Why Do We Need Embeddings in RAG?

  • Problem: Pure keyword search can miss context and semantic meaning.
  • Embeddings power semantic search: retrieve relevant content even if different words are used.
  • Embeddings make RAG powerful and accurate.

Exercise: Manual Embeddings

Can you embed words by hand?

  1. Draw a 2D coordinate system with two axes — you decide what they mean!
    • e.g. x = size (small → large), y = domestic → wild
  2. Place these words on your map:
    • 🐱 cat, 🐶 dog, 🐯 tiger, 🐻 bear, 🐹 hamster, 🦁 lion, 🐕 wolf, 🐇 rabbit
  3. Compare with your neighbour — do you agree?
  4. Which of the other animals ended up closest to “cat” on your map?
    • What does that tell us about their relationship?
  • This is exactly what real embeddings do — but in hundreds or thousands dimensions instead of 2!

Debrief: What did we learn?

  • Axes matter: the dimensions we choose shape the “meaning”
  • Real embeddings learn their axes from billions of words — we just made them up
  • Key insight: similarity = distance. Close = related. Far = different.
  • A vector DB just asks: “what’s closest to this query vector?”
  • Think of a vector DB as a filter on your data

Embedding Models

  • We placed words manually — in reality, specialised LLMs do this automatically
  • Called embedding models — trained specifically to convert text into vectors
  • Examples: text-embedding-ada-002 (OpenAI), nomic-embed-text, mxbai-embed
  • Different from chat models — they don’t generate text, they output numbers
  • You need to use the same model for indexing and querying

Semantic Search Basics

Keyword search: matches your exact words - Search “car repair” → finds “car repair”. Search “fixing automobiles” → finds nothing.

Semantic search: understands what you mean - Search “fixing automobiles” → still finds the car repair docs, because the meaning is the same.

  • Your query is turned into a vector
  • Stored documents are also vectors
  • Finds the ones pointing in the same “direction” — closest in meaning
