Recap: the coding agent

  • Week 9: the agent reads the repository, edits files, runs commands
  • It works from what you tell it — and fills every gap with a guess
  • The guesses are plausible, which is why they are hard to spot
  • The longer the task, the more guesses compound

Why vague requests fail

  • “Add login” — which users? Which provider? What happens on failure?
  • The agent cannot ask the stakeholders. It can only ask you — if told to
  • Context is lost between sessions: tomorrow’s agent knows nothing of today’s decisions
  • Without acceptance criteria, “done” means “the agent stopped”

Built in: plan mode

  • Claude Code and Codex both have a plan mode
  • The agent investigates and proposes a plan — but changes nothing
  • You review, correct, then approve before any code is written
  • Claude Code: Shift+Tab, or claude --permission-mode plan
  • Plan before code — the first step towards spec-driven development

Built in: /goal

  • /goal <condition> — the agent keeps working until the condition is met
  • Claude Code checks the goal before it stops; Codex adds a token budget and /goal pause, /goal resume, /goal clear
  • A goal is an acceptance criterion the agent checks itself
  • Example: /goal all tests in tests/ pass and the README describes setup
  • The agent judges its own work — you still review

Spec-driven development

  • Write what and why before how
  • The spec is the source of truth — code is generated from it
  • Requirements and success criteria must be testable
  • Decisions live in files in the repository, not in a chat history
  • Keep checking that the code still matches the spec

The context engineering view

  • Week 5: an agent is only as good as its context
  • A spec is curated, versioned context
  • Each step produces a file the next step reads
  • Small, focused steps instead of one huge prompt
  • The repository becomes the agent’s memory

GitHub Spec Kit

  • Open-source toolkit from GitHub: https://github.com/github/spec-kit
  • A CLI (specify) that sets up the structure
  • Templates, scripts and agent instructions (skills/commands)
  • Works with many coding agents: Claude Code, Codex, Copilot, opencode and others
  • Not tied to one provider — the process is the point, not the tool

Getting started

# install the CLI (requires uv)
uv tool install specify-cli --from git+https://github.com/github/spec-kit.git

# create a project for your coding agent
specify init my-project --integration claude

# check that the required tools are installed
specify check
  • --integration picks the agent: claude, codex, copilot, …
  • --script sh | ps | py picks the script type (ps on Windows)

What specify init creates

.specify/
  memory/constitution.md      # project-wide principles
  templates/                  # spec, plan, tasks, checklist templates
  scripts/bash/               # create-new-feature.sh, setup-plan.sh, ...
  workflows/speckit/workflow.yml
.claude/ or .agents/skills/   # one skill/command per step
specs/
  001-feature-name/           # one folder per feature
    spec.md  plan.md  tasks.md
    research.md  data-model.md  quickstart.md
    contracts/  checklists/
  • Everything is Markdown, YAML and shell — you can read all of it

The workflow

Constitution → Specify → Clarify → Plan → Tasks → Implement → Converge

  • Each step is one skill: speckit.constitution, speckit.specify, …
  • Each step reads the previous files and writes a new one
  • Extra quality steps: checklist and analyze
  • Bonus: taskstoissues turns tasks into GitHub issues

Constitution

  • .specify/memory/constitution.md
  • Project-wide principles and constraints that apply to every feature
  • E.g. “Test first”, “No personal data in the repository”, “Python and SQLite only”
  • The plan step checks against it: Constitution Check is a gate
  • Violations must be justified in writing

Specify

  • Input: a natural-language description of the feature
  • A script creates a numbered folder and branch: specs/001-...
  • Output: spec.md — user scenarios, functional requirements (FR-001), success criteria (SC-001)
  • What and why only — no technology choices
  • Unknowns are marked [NEEDS CLARIFICATION: ...] — at most 3

The spec is user stories

  • spec.md is built around prioritized user stories: P1, P2, P3, …
  • Each story must be independently testable — P1 alone is a viable MVP
  • Each story has acceptance scenarios:
### User Story 1 - [Brief Title] (Priority: P1)
**Why this priority**: ...
**Independent Test**: ...
**Acceptance Scenarios**:
1. **Given** [initial state], **When** [action], **Then** [expected outcome]
  • Plus functional requirements (FR-001) and success criteria (SC-001)

Tasks live under the user stories

tasks.md is organized in phases:

Phase Contents
1. Setup Shared infrastructure — project structure, dependencies
2. Foundational Blocking prerequisites — no story can start before this
3. User Story 1 (P1) 🎯 MVP Tasks tagged [US1]
4. User Story 2 (P2) Tasks tagged [US2]
… …
N. Polish Cross-cutting concerns
  • Each story phase ends with a checkpoint: the story works on its own
  • Build and demo P1 first — then P2, and so on

Clarify

  • Reads spec.md and looks for gaps and ambiguity
  • Asks up to 5 targeted questions, often with options to choose from
  • Writes the answers back into the spec
  • This is the agent asking instead of guessing — by design
  • Your job: answer as the business, not as the developer

Plan

  • The spec says what — the plan says how
  • Output: plan.md plus research.md, data-model.md, contracts/, quickstart.md
  • Language, stack, architecture, data model, interfaces
  • Checked against the constitution before and after design

Tasks

  • Breaks the plan into small, concrete tasks in tasks.md
  • IDs and markers the agent can work from:
- [ ] T001 Create project structure per implementation plan
- [ ] T003 [P] Configure linting and formatting tools
- [ ] T010 [P] [US1] Contract test for /lessons in tests/contract/...
  • [P] = can run in parallel (different files, no dependencies)
  • [US1] = belongs to user story 1 — each story is a deliverable slice

Implement and Converge

  • Implement works through tasks.md and ticks off [x] as it goes
  • Converge compares the code against spec, plan and tasks
  • Converge does not edit code — it appends missing work as new tasks
  • Loop: implement → converge → implement → … until converged
  • Converge is the agent’s check — your review is still needed

Spec Kit is automation

  • The skills are the automation: the procedure is written down once and the agent follows it every time
  • Scripts do the deterministic parts: folders, branches, numbering, file paths
  • The LLM does the parts that need judgement: writing, asking, planning, coding
  • Same split as in n8n: deterministic nodes and AI nodes

Workflows with gates

.specify/workflows/speckit/workflow.yml:

steps:
  - id: specify
    command: speckit.specify
  - id: review-spec
    type: gate
    message: "Review the generated spec before planning."
    options: [approve, reject]
    on_reject: abort
  - id: plan
    command: speckit.plan
  - id: review-plan
    type: gate
  - id: tasks
    command: speckit.tasks
  - id: implement
    command: speckit.implement
  • specify workflow run speckit -i spec="..."
  • AI steps, human gates — the human-in-the-loop from week 3, as configuration

Hooks and extensions

  • Steps can call hooks, e.g. before_implement and after_implement
  • Extensions and presets add or change steps and templates
  • You can change the templates and skills yourself — they are just files
  • Your process, written down as instructions the agent follows

Where it breaks

  • The agent writes plausible specs — reviewing them is real work
  • Specs drift from code if nobody re-runs converge or updates the spec
  • Overkill for small changes — not every bug fix needs a constitution
  • Lots of generated text: more to review, more tokens
  • The human still owns the decisions

Working with the agent

  • One step at a time: review before moving on
  • Ask for evidence: which requirement does this code satisfy?
  • Don’t let it invent business rules — make it ask
  • Inspect the diff after broad edits
  • Get a second opinion: another agent or session reviews the spec

Demo: the two-week project as a spec

  • Input: the two-week project description (RAG) — vector + graph RAG, n8n, Neo4j, agent
  • specify init in VS Code, then step by step: Constitution → Specify → Clarify → Plan → Tasks
  • After each step: open the file — what will the next step read?
  • Clarify: you answer the agent’s questions
  • Look for what the agent assumed about your project

Exercise: your two-week project, spec-driven

  • Run Spec Kit on your own two-week project case
  • specify init with your own coding agent
  • Constitution → Specify → Clarify → Plan → Tasks
  • Review each file before moving on
  • Compare: what does the spec contain that your project did not have?
  • If time: implement one user story, then run Converge

From Spec Kit to the factory

  • Spec Kit automates the steps within one feature
  • A factory automates the pipeline across many specs
  • Spec → agent → question → pull request → review
  • That is your final project
