RAG

Vector RAG — recap

  1. Split the text into chunks
  2. Create embeddings and store the text, vector, and source
  3. Create an embedding of the question
  4. Find chunks with similar vectors
  5. Give the retrieved texts to an LLM as context
  • Use the same embedding model for documents and questions
  • The embedding model’s dimensions must match the index

Retrieval finds the context; an LLM call then needs to formulate the answer.

Vector query

CALL db.index.vector.queryNodes(
  'course_chunks', 3, $embedding
)
YIELD node, score
RETURN node.text, node.source, score
  • The score ranks similarity between vectors
  • It does not tell you whether an answer is correct

Vector RAG with an agent

Retrieval can happen at different points in the workflow:

  1. The workflow retrieves context and passes it to the agent
  2. The agent gets a tool and decides when to search
  3. The workflow retrieves initial context; the agent can search further

In all three cases, the agent needs both the question and the retrieved sources.

Retrieve first → give context to the agent

Question → Embed → Vector search → Context → Agent
  • The workflow decides to search and how much to retrieve
  • Include the question, retrieved texts, and sources in the agent’s input
  • The agent does not need to call a retrieval tool itself
  • Useful when you always need to search the same source

Show Parse Results in the existing retrieval workflow. Combine the chunks into one context and pass it to the agent with the original question. A regular LLM node can also formulate the answer if the agent’s other tools or decisions are not needed.

Retrieval as a tool

Question → Agent → Search tool → Context → Agent
  • The agent chooses search terms and can search multiple times
  • Tool: receive search text → embed → search → return text and sources
  • Describe what the tool searches and when it should be used
  • Check the execution log to see whether the agent actually used the tool

In n8n, retrieval can live in a sub-workflow connected to the agent through a workflow tool. The tool input is search text; the output is relevant chunks with sources. Embedding is part of the tool, not the agent’s task.

Combining initial context and a search tool

Question → Retrieval → Agent with initial context
                          ↕
                      Search tool
  • The workflow handles the first search
  • The agent can retrieve more if the context is insufficient
  • Example: find relevant recipes first; let the agent search for alternatives
  • Limit the number of searches and ask the agent to say when sources are insufficient

None of these patterns guarantees a correct answer. Inspect both the retrieved context and the answer. Tool use requires a model that can call tools reliably; retrieval before the agent is also allowed in the project brief.

Graph RAG — recap

  • Nodes: things in your domain
  • Relationships: connections between those things
  • Properties: information on nodes and relationships
  • A query finds relevant connections
  • The result is given to an LLM as context

Example prompt: graph extraction

From this wiki text, suggest nodes, node types, relationship types, and properties. For each relationship, include the supporting sentence. Use only information in the text and flag anything uncertain.

Node types, relationships, and metadata

  • Node types: what kinds of things matter? For a film wiki: Film, Person, Genre
  • Relationship types: how are they connected? (Person)-[:DIRECTED]->(Film)
  • Properties and metadata: names, release year, source URL, and date retrieved
  • Review the data: merge duplicate names, use consistent types, and check relationship direction
  • Try your questions: can the proposed graph answer them? Adjust the model and extraction before importing more pages

Your task: work through a small sample of your own data. Decide which types and properties to keep, and correct the AI’s suggestions.

Neo4j locally

  • Neo4j Desktop: create a local instance, choose a password, and start it
  • Open Query/Browser and select the database
  • Alternative: run Neo4j in Docker
  • The same database can contain both graphs and embeddings

Instance, database, and connection

  • Neo4j Desktop / Docker starts and manages an instance
  • An instance is the running Neo4j server
  • A database holds data; our database is called neo4j
  • Browser / Query is the interface for inspecting data and running Cypher
  • n8n accesses the database through a connection with a username and password

What is Cypher?

  • Cypher is Neo4j’s query language — a similar role to SQL in a relational database
  • Queries describe patterns of nodes and relationships: (node)-[:RELATIONSHIP]->(node)

Find topics — like selecting rows in SQL:

MATCH (t:DemoTopic)
RETURN t.name

Follow a relationship — which topics depend on Agents?

MATCH (t:DemoTopic)-[:DEPENDS_ON]->(:DemoTopic {name: 'Agents'})
RETURN t.name

The spring lecture’s Project/Feature and Course/prerequisite examples use the same pattern. Here we use the DemoTopic graph from this demonstration. The first query returns all topic names; the second returns Tools, which depends directly on Agents. MATCH finds the pattern; RETURN selects the output.

Nodes, labels, and properties

(:DemoTopic {name: 'RAG', source: 'Classroom example'})
  • DemoTopic is a label that groups this kind of node
  • name and source are properties with values
  • A relationship has a type and a direction:
(RAG)-[:DEPENDS_ON]->(Tools)

Create data with Cypher

MERGE (a:DemoTopic {name: 'Agents'})
MERGE (t:DemoTopic {name: 'Tools'})
MERGE (t)-[:DEPENDS_ON]->(a)
RETURN t, a
  • MERGE: find the pattern or create it if it is missing
  • CREATE: creates new data every time
  • Reuse a stable key when importing the same data again
  • Consistent naming avoids separate nodes for, say, Agents and agents

Find data with Cypher

MATCH (t:DemoTopic)-[:DEPENDS_ON]->(a:DemoTopic)
WHERE a.name = 'Agents'
RETURN t.name AS topic, a.name AS dependsOn
  • MATCH describes the pattern we are looking for
  • WHERE filters; RETURN selects the data we get back
  • Here we get direct connections: Tools → Agents
  • [:DEPENDS_ON*1..3] follows between one and three hops

Vector and graph in the same database

  • Graph: labels, properties, and relationships
  • Vector: an embedding is stored as a property on a node
  • A vector index makes it possible to search for similar embeddings
  • In our demo: Chunk.text, Chunk.source, and Chunk.embedding
  • The same Neo4j database, with different ways of finding data

Demo: retrieve connections

Open Wednesday - Graph RAG. Query Graph uses:

MATCH (t:DemoTopic)-[:DEPENDS_ON*1..3]->
      (:DemoTopic {name: $topic})
RETURN DISTINCT t.name AS topic, t.source AS source
ORDER BY topic
  • Parameter: topic = Agents
  • Result: RAG and Tools
  • The query is fixed; the value is passed as a parameter

Reading the graph query

Question: which topics depend on Agents?

RAG ──DEPENDS_ON──> Tools ──DEPENDS_ON──> Agents
  • $topic is the value supplied by n8n: Agents
  • MATCH finds topics with a path pointing to Agents
  • *1..3 allows one to three steps: Tools is one step away; RAG is two
  • RETURN DISTINCT returns each topic/source pair once
  • ORDER BY topic sorts the results: RAG, then Tools
